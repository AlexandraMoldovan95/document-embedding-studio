Rate limiting

Rate limiting protects the API from being overwhelmed by too many requests in a short window. When a client exceeds its allotted rate, the API returns a 429 Too Many Requests status code, along with a Retry-After header telling the client how many seconds to wait. Clients should treat 429 as a signal to back off, not as a permanent failure.

Retry strategy

A well-behaved client retries the same request later rather than giving up or hammering the endpoint again immediately. The recommended strategy is exponential backoff with jitter: double the wait time after each failed attempt, and add a small random delay so that many clients retrying at once don't all collide on the same retry schedule.

Authentication errors: 401 vs 403

Authentication errors come in two main flavors that are often confused. A 401 Unauthorized means the request has no valid credentials at all - the API key is missing, malformed, or expired. A 403 Forbidden means the credentials are valid, but the authenticated caller doesn't have permission to perform this specific action.

Idempotency keys

Idempotency keys let a client safely retry a request that may have already succeeded, without causing it twice - for example, a payment that timed out before the response arrived. The client generates a unique key per logical operation and sends it in a header; the server stores the result of the first request under that key.

Timeouts

Timeouts need a value on both sides of a request. A client-side timeout that's too short causes retries of requests that were actually about to succeed, wasting capacity on both ends. As a rule of thumb, the client's timeout should be a little longer than the server's own maximum processing time for that endpoint.

Error response shape

Every error response follows the same JSON shape across the API: a machine-readable code field for programmatic branching, a human-readable message meant for logs and debugging, and an optional details object with field-specific validation errors. Keeping this shape consistent means client code can handle errors generically in one place.
